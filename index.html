AULA INTRODUTÓRIA · LABORATÓRIO

O que você vai aprender

Entender o papel de cada componente, explicar o caminho de uma requisição e planejar a publicação de uma aplicação MVC.

Projeto proposto: uma página “Minha primeira publicação”, com nome do aluno e mensagem de boas-vindas, sem banco de dados.

Pré-requisitos: noções de HTML e terminal, Git no computador, conta Azure com permissão para criar recursos e um domínio cujo DNS você possa editar. A criação da VM e a instalação do Docker e do Nginx estão explicadas abaixo. O exemplo usa .NET 8; o SDK local é opcional para quem executar somente na VM.

1. Visão geral

O objetivo é levar uma aplicação ASP.NET Core MVC que funciona no computador do desenvolvedor para uma máquina virtual no Azure, protegê-la e disponibilizá-la na internet.

Usuário → HTTPS :443 → Nginx → Aplicação MVC no Docker

2. Etapas da publicação

① Projeto MVC

Você desenvolve e testa sua aplicação .NET localmente. Aqui ficam Controllers, Models, Views, serviços e acesso ao banco.

② VM Azure

É um computador virtual na nuvem. Podemos criar uma VM com Ubuntu Linux, CPU, RAM, disco, rede e IP público.

③ Git

Controla versões do código e facilita levá-lo até o servidor. Na VM podemos executar git clone para obter o projeto.

④ Docker

Empacota a aplicação e suas dependências em uma imagem. Ao executar essa imagem, temos um container.

⑤ Nginx

Fica na frente da aplicação como proxy reverso. Recebe requisições externas e encaminha para a aplicação que está no container.

⑥ Rede e HTTPS

Configuramos domínio, DNS, certificado TLS, portas, NSG e firewall para permitir acesso seguro.

⑦ Aplicação publicada

O usuário finalmente acessa algo como https://meusite.com sem precisar conhecer a porta interna da aplicação.

3. Conceitos importantes

🔐 SSH

Secure Shell permite administrar a VM Linux remotamente pelo terminal. Normalmente utiliza a porta 22.

ssh usuario@ip-da-vm

🌐 DNS

Transforma um domínio amigável, como meusite.com, no endereço IP correspondente ao servidor.

🔒 Certificado TLS

Permite autenticar o servidor para o domínio e estabelecer uma conexão HTTPS criptografada. Serviços como Let's Encrypt podem emitir certificados gratuitamente.

↪️ Proxy reverso

O Nginx recebe a requisição em 443 e pode encaminhá-la internamente para a aplicação em 8080.

🛡️ NSG

O Network Security Group do Azure possui regras que controlam quais conexões podem chegar ou sair dos recursos de rede.

🔥 Firewall

Dentro do Linux também podemos controlar tráfego, por exemplo com ufw. Assim temos mais de uma camada de proteção.

4. Portas de rede

O IP identifica a máquina. A porta ajuda a identificar qual serviço naquela máquina deve receber a conexão.

PortaUso comumNo projeto
22SSHAdministração da VM
80HTTPAcesso web sem TLS / redirecionamento
443HTTPSAcesso público seguro
8080Aplicação webPode ser usada internamente pelo container
1433SQL ServerBanco de dados, quando aplicável

5. Como uma requisição percorre o sistema?

Antes da conexão, o navegador resolve o domínio pelo DNS, ou usa uma resposta em cache. O DNS resolve o endereço; ele não encaminha o tráfego HTTP.

Navegador → IP da VM → NSG / Firewall → Nginx :443 → Aplicação MVC no container :8080
💡 Ideia-chave: a porta 8080 da aplicação não precisa ficar aberta para toda a internet. O público conversa com o Nginx pela porta 443, e o Nginx encaminha a requisição para a aplicação internamente.

PONTO DE PARTIDA · COMPUTADOR LOCAL

1. Tenha uma aplicação pronta para publicar

Use o ZIP acima para acompanhar exatamente os comandos. O exemplo contém um Model com os dados da mensagem, um Controller que os prepara e uma View que gera a página. Não precisa de banco de dados.

Se tiver o SDK .NET 8 instalado, abra o terminal na pasta extraída e faça o teste abaixo. Sem o SDK, siga para a VM: o Docker fará a compilação.

dotnet run --urls http://localhost:5080

Confira: abra http://localhost:5080. Deve aparecer “Minha primeira publicação”. Use Ctrl+C para encerrar.

Já tenho meu próprio projeto MVC

Primeiro conclua com o exemplo. Para adaptar, alinhe a versão do SDK e do runtime no Dockerfile com o TargetFramework do seu projeto e ajuste o nome do .csproj e da DLL. Aplicações com autenticação, banco ou uploads exigem configuração e persistência adicionais. A configuração de proxy em Program.cs deve ser integrada ao pipeline existente, antes dos middlewares que dependem do protocolo.

ETAPA 2 · PORTAL AZURE → POWERSHELL → SSH

2. Crie e prepare a VM

2.1 · Criar o servidor no portal

  1. Acesse portal.azure.com, procure Máquinas virtuais e escolha Criar → Máquina virtual do Azure.
  2. Selecione sua assinatura. Crie um grupo exclusivo chamado rg-aula-mvc e nomeie a VM como vm-aula-mvc.
  3. Escolha uma região disponível para sua assinatura, imagem Ubuntu Server 24.04 LTS — x64 e um tamanho com pelo menos 2 vCPU e 4 GiB de RAM para compilar o exemplo. Compare o custo exibido.
  4. Em autenticação, escolha Chave pública SSH, usuário azureuser e gerar novo par de chaves. Nomeie a chave vm-aula-mvc_key.
  5. Em portas de entrada, escolha inicialmente Nenhuma. Na aba Rede, mantenha uma rede e sub-rede novas e associe um IP público. Confira que o IP público usa alocação estática.
  6. Revise e crie. Baixe a chave privada vm-aula-mvc_key.pem quando solicitado e guarde-a. Ela não deve ir para o Git.
  7. Ao concluir, abra a VM e anote seu Endereço IP público.

2.2 · Liberar somente seu acesso administrativo

Na VM, abra Configurações de rede / Rede e o NSG associado. Adicione estas regras de entrada. Os nomes da interface podem variar. Use prioridades livres, menores que as regras padrão de bloqueio.

PrioridadeNomeOrigemDestino / portaProtocolo / ação
300Permitir-SSH-meu-IPSeu IPv4 público /32Qualquer / 22TCP / Permitir
310Permitir-HTTPInternetQualquer / 80TCP / Permitir
320Permitir-HTTPSInternetQualquer / 443TCP / Permitir

Em todas, deixe a porta de origem como *. Não crie liberação para 8080. Se houver NSG na sub-rede e na interface, ambos precisam permitir o tráfego. Para descobrir seu IPv4 público, execute no computador:

curl.exe -4 https://api.ipify.org

2.3 · Conectar com a chave privada

Substitua o IP e ajuste o caminho se a chave estiver em outra pasta:

ssh -i "$env:USERPROFILE\Downloads\vm-aula-mvc_key.pem" azureuser@IP_PUBLICO_DA_VM

Na primeira conexão, confira a impressão digital da chave do servidor. No portal, o recurso Executar comando → RunShellScript permite executar ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub para comparar com a chave ED25519 exibida pelo SSH. Confirme com yes se corresponder.

SSH informa que a chave privada tem permissões abertas

No PowerShell, limite a leitura da sua chave ao usuário atual e tente conectar novamente:

$chaveAula = "$env:USERPROFILE\Downloads\vm-aula-mvc_key.pem"
icacls $chaveAula /inheritance:r
icacls $chaveAula /grant:r "$($env:USERNAME):(R)"

Confira com icacls $chaveAula se não restaram permissões explícitas para outros usuários. Em Linux/macOS, use chmod 600 caminho/da/chave.pem.

2.4 · Atualizar o Ubuntu e configurar o firewall

A partir daqui, use o terminal conectado à VM. Execute os blocos um por vez.

sudo apt-get update
sudo apt-get upgrade -y
sudo apt-get install -y git curl ca-certificates nginx ufw dnsutils snapd nano
cat /etc/os-release

Se a atualização pedir reinicialização, execute sudo reboot, aguarde e conecte de novo por SSH. Antes de ativar o firewall, substitua o IP abaixo pelo IPv4 público do seu computador:

sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow from SEU_IP_PUBLICO to any port 22 proto tcp
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw enable
sudo ufw status numbered

Confira: Ubuntu 24.04 e UFW ativo, com 22 restrita ao seu IP e 80/443 liberadas. Abra uma segunda conexão SSH antes de fechar a primeira. Se seu IP mudar, ajuste a regra do NSG e do UFW; o Executar comando do portal ajuda a recuperar o acesso.

Referência: criação de VM Linux no Azure.

ETAPA 4 · BASH NA VM

4. Instale o Docker e execute a aplicação

4.1 · Instalar Docker Engine e Compose

Estes comandos são para a VM Ubuntu 24.04 x64 nova desta aula. Adicione a chave e o repositório oficial:

sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc
echo "deb [arch=amd64 signed-by=/etc/apt/keyrings/docker.asc] https://download.docker.com/linux/ubuntu noble stable" | sudo tee /etc/apt/sources.list.d/docker.list
sudo apt-get update
sudo apt-get install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
sudo systemctl enable --now docker
sudo docker run --rm hello-world
sudo docker compose version

Confira: o teste mostra “Hello from Docker!” e o Compose informa sua versão. O guia usa sudo docker em todos os comandos.

4.2 · Entender os arquivos do exemplo

O Dockerfile já está no ZIP. A primeira imagem compila o projeto; a segunda contém apenas o runtime e os arquivos publicados.

FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
WORKDIR /src
COPY AulaMvc.csproj ./
RUN dotnet restore AulaMvc.csproj
COPY . ./
RUN dotnet publish AulaMvc.csproj -c Release -o /out --no-restore

FROM mcr.microsoft.com/dotnet/aspnet:8.0 AS final
WORKDIR /app
COPY --from=build /out ./
ENV ASPNETCORE_HTTP_PORTS=8080
USER app
EXPOSE 8080
ENTRYPOINT ["dotnet", "AulaMvc.dll"]

O compose.yaml também está pronto. Ele publica 127.0.0.1:8080:8080: a primeira porta é da VM e a segunda é do contêiner. O vínculo com 127.0.0.1 mantém esse acesso local. O arquivo configura reinício automático e limite dos logs.

compose.yaml completo (incluído no ZIP)
name: aula-mvc
services:
  web:
    build: .
    image: aula-mvc:local
    restart: unless-stopped
    ports:
      - "127.0.0.1:8080:8080"
    environment:
      ASPNETCORE_ENVIRONMENT: Production
      ASPNETCORE_HTTP_PORTS: "8080"
      Aluno: ${ALUNO:-Minha turma}
      TrustedProxy: ${TRUSTED_PROXY:?Configure TRUSTED_PROXY no arquivo .env}
    networks:
      - aula
    logging:
      driver: json-file
      options:
        max-size: "10m"
        max-file: "3"
networks:
  aula:
    external: true
    name: aula-net

4.3 · Criar a rede e configurar as variáveis

Crie a rede uma vez. Se repetir a etapa e ela já existir, apenas confira com sudo docker network inspect aula-net e continue. O Docker escolhe uma faixa disponível.

cd ~/apps/aula-mvc
sudo docker network create aula-net
PROXY_AULA=$(sudo docker network inspect aula-net --format '{{(index .IPAM.Config 0).Gateway}}')
printf 'ALUNO=Minha turma\nTRUSTED_PROXY=%s\n' "$PROXY_AULA" > .env
chmod 600 .env
nano .env

No editor, personalize ALUNO=Seu Nome. Mantenha o IP gerado em TRUSTED_PROXY. Salve com Ctrl+O, Enter e saia com Ctrl+X. O comando printf recria o .env; não o repita se quiser preservar sua personalização.

O Nginx vai acessar a porta local e o tráfego chegará ao contêiner pelo gateway dessa rede. O Program.cs do exemplo confia especificamente nesse endereço para interpretar X-Forwarded-Proto e X-Forwarded-For. Assim, a página reconhece HTTPS após a configuração do certificado. O .env fica fora do Git e da imagem.

Como o Program.cs reconhece o proxy

O middleware processa os cabeçalhos antes das rotas e aceita o IP de proxy configurado. O Nginx cuida do redirecionamento para HTTPS neste exemplo.

using System.Net;
using Microsoft.AspNetCore.HttpOverrides;

var builder = WebApplication.CreateBuilder(args);
builder.Services.AddControllersWithViews();
builder.Services.Configure<ForwardedHeadersOptions>(options =>
{
    options.ForwardedHeaders = ForwardedHeaders.XForwardedFor | ForwardedHeaders.XForwardedProto;
    options.ForwardLimit = 1;
    if (IPAddress.TryParse(builder.Configuration["TrustedProxy"], out var proxy))
    {
        options.KnownProxies.Add(proxy);
        options.KnownProxies.Add(proxy.MapToIPv6());
    }
});

var app = builder.Build();
app.UseForwardedHeaders();
// Neste laboratório, o Nginx faz o redirecionamento HTTP -> HTTPS.
app.UseRouting();
app.MapControllerRoute("default", "{controller=Home}/{action=Index}/{id?}");
app.MapGet("/health", () => Results.Ok(new { status = "ok" }));
app.Run();

4.4 · Compilar, iniciar e testar

sudo docker compose config --quiet
sudo docker compose up -d --build
sudo docker compose ps
sudo docker compose logs --tail=50 web
curl -i http://127.0.0.1:8080/health

Confira: serviço web em execução, porta 127.0.0.1:8080 e resposta HTTP/1.1 200 OK com {"status":"ok"}. A primeira compilação pode demorar. Se o curl falhar enquanto a aplicação inicia, aguarde alguns segundos e repita. Não avance se persistir.

Referências: Docker Engine no Ubuntu e redes bridge do Docker.

ETAPA 5 · BASH NA VM

5. Configure o Nginx como proxy reverso

5.1 · Criar o arquivo do site

sudo systemctl enable --now nginx
sudo nano /etc/nginx/sites-available/aula-mvc

Cole o conteúdo abaixo no editor. Substitua aula.seudominio.com pelo seu domínio real. As variáveis com $ pertencem ao Nginx: mantenha-as exatamente como estão.

server {
    listen 80;
    server_name aula.seudominio.com;

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

Salve com Ctrl+O, Enter e saia com Ctrl+X. Este arquivo começa com HTTP; o Certbot adicionará HTTPS na próxima etapa.

5.2 · Ativar e validar o site

sudo ln -s /etc/nginx/sites-available/aula-mvc /etc/nginx/sites-enabled/aula-mvc
sudo nginx -t

Se o link já existir, não precisa recriá-lo. Só recarregue quando a validação indicar syntax is ok e test is successful:

sudo systemctl reload nginx
curl -i -H 'Host: aula.seudominio.com' http://127.0.0.1/health

Confira: status 200 e JSON com status ok, agora passando pelo Nginx. A página padrão do Nginx pode continuar aparecendo quando você acessa apenas o IP; nosso site é selecionado pelo nome do domínio.

5.3 · Testar de fora da VM antes do DNS

curl.exe --resolve aula.seudominio.com:80:IP_PUBLICO_DA_VM http://aula.seudominio.com/health

Esse teste usa o IP informado e envia o nome correto ao Nginx. Deve retornar o JSON. Se falhar aqui, mas funcionar dentro da VM, confira NSG, firewall e IP público.

Referência: ASP.NET Core atrás do Nginx.

ETAPA 6 · PAINEL DNS → BASH NA VM

6. Aponte o domínio e habilite HTTPS

6.1 · Criar o registro DNS

No provedor que gerencia o DNS do seu domínio, adicione um registro A. Para aula.seudominio.com, normalmente o campo Nome/Host recebe aula; o valor recebe o IPv4 público da VM. Use TTL de 300 segundos, se disponível. Se o provedor oferecer proxy/CDN, deixe somente DNS nesta prática.

Não crie um registro AAAA se não configurou IPv6. Se houver um AAAA antigo para esse subdomínio, corrija-o ou remova-o para evitar acesso ao servidor errado.

dig +short A aula.seudominio.com @1.1.1.1
dig +short AAAA aula.seudominio.com @1.1.1.1
curl -I http://aula.seudominio.com

Confira: o registro A retorna o IPv4 da VM; no cenário sem IPv6, AAAA não retorna endereço. O site deve abrir por HTTP também no seu computador. Aguarde a propagação se a resposta ainda estiver antiga.

Sem um domínio sob seu controle, você pode concluir o teste HTTP pelo comando --resolve da etapa anterior. Para completar o HTTPS deste roteiro, é necessário um domínio que resolva para a VM.

6.2 · Emitir e instalar o certificado

Com o DNS correto e a porta 80 acessível pela internet, instale o Certbot e solicite o certificado. Substitua o domínio; informe seu e-mail quando solicitado e leia os termos apresentados.

sudo snap install core
sudo snap refresh core
sudo snap install --classic certbot
sudo /snap/bin/certbot --nginx -d aula.seudominio.com --redirect
sudo nginx -t

O Certbot modifica o site do Nginx para usar o certificado e redirecionar HTTP para HTTPS. Não substitua esse arquivo pelo bloco HTTP da etapa anterior depois da emissão.

6.3 · Conferir renovação

sudo /snap/bin/certbot certificates
sudo /snap/bin/certbot renew --dry-run
systemctl list-timers --all | grep certbot

Confira: certificado para seu domínio, simulação de renovação bem-sucedida e agendamento de renovação do snap. Mantenha o domínio apontado para a VM e a porta 80 disponível para validações HTTP futuras.

Referência: instruções oficiais do Certbot para Nginx.

ETAPA 7 · VALIDAÇÃO E ENTREGA

7. Confira a publicação completa

7.1 · Testar a partir do seu computador

curl.exe -I http://aula.seudominio.com
curl.exe -I https://aula.seudominio.com
curl.exe https://aula.seudominio.com/health
Test-NetConnection IP_PUBLICO_DA_VM -Port 8080
  • HTTP: redirecionamento 301 ou 308 para a URL HTTPS.
  • HTTPS: status 200, sem ignorar a validação do certificado.
  • /health: JSON com status ok.
  • Porta 8080: TcpTestSucceeded: False. O teste pode demorar até expirar.

Abra https://aula.seudominio.com no navegador. Confira seu nome, ambiente Production e protocolo reconhecido https. Se aparecer http, confira TRUSTED_PROXY no .env, o gateway da rede e os cabeçalhos do Nginx.

cd ~/apps/aula-mvc
sudo docker compose logs --tail=100 web
sudo tail -n 30 /var/log/nginx/access.log
sudo tail -n 30 /var/log/nginx/error.log
sudo systemctl status nginx --no-pager

Entrega: URL HTTPS, captura da página com seu nome, resposta do /health e uma explicação de como Nginx, Docker e MVC participam da requisição.

7.3 · Publicar uma alteração depois

Edite a View no projeto do computador. Na pasta local, envie o commit:

git add .

Para encerrar a prática, salve sua entrega e, no portal, abra o grupo rg-aula-mvc, confira que contém somente recursos desta aula e exclua o grupo. A exclusão remove a VM e seus dados. Remova também o registro DNS que apontava para ela. Desalocar a VM interrompe o processamento, mas discos e outros recursos podem continuar sendo cobrados.

Como investigar problemas

Conexão esgotada

Confira IP, DNS, regras do NSG, firewall e se o serviço está ouvindo na porta esperada.

Erro 502

Verifique se a aplicação está em execução, a porta de destino configurada no Nginx e os logs do contêiner.

Aviso de certificado

Confira o domínio, a validade do certificado e a configuração TLS do Nginx.

8. Perguntas de revisão

Tente responder antes de abrir a explicação.

Qual é a diferença entre imagem e contêiner?

A imagem é o pacote usado como base. O contêiner é uma instância criada a partir dela, com seu próprio estado de execução.

Por que usar o Nginx na frente da aplicação?

Ele recebe as conexões públicas, termina o HTTPS e encaminha as requisições para a aplicação interna.

O DNS encaminha a requisição HTTP?

Não. Ele resolve o nome para um endereço. A conexão web é feita com o endereço obtido.

A porta da aplicação deve estar aberta na internet?

Não neste cenário. A aplicação atende localmente ao Nginx. O usuário acessa as portas web públicas.

O que comprova que a publicação funcionou?

A página esperada responde pelo domínio com HTTPS válido, HTTP redireciona para HTTPS e os logs permitem conferir as requisições.
